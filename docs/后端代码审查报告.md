# 麦麦同席 · 后端代码审查报告

- **审查范围**：`mmtx/app/`（server / mcd_mcp / rules / strategy / allocate / explain / store / ticket）、`mmtx/run.py`
- **规模**：约 3,200 行（不含测试）
- **审查维度**：代码结构、逻辑正确性、潜在缺陷、安全性、性能、可维护性
- **方法**：逐文件精读 + 对疑点做可执行验证（验证脚本结论已写入各条目）+ 回归测试基线（`unittest discover tests`，34 项全通过）
- **基线结论**：分层清晰、失败语义（ok / source / error.code）设计成熟、「不编造价格」的降级路径落实到位；但**分账口径存在可复算性破坏**、**硬约束存在漏判**、**缓存会放大故障**三类问题需要优先修复。

问题按严重程度分为 P0（破坏核心承诺）/ P1（高）/ P2（中）/ P3（低与可维护性）。

## 二、P0 — 破坏核心承诺（建议立即修）

### P0-1 分账金额重复计数，分摊口径不可复算
**位置**：`app/allocate.py:41-63`（`item_gross`）
**原因**：`official[code] = official.get(code, 0) + int(subtotal)` 按 productCode 聚合官方分项金额，随后 `for it in items: out.append(int(official[code]))` 把**聚合后的总额**赋给**每一行**。当同一 productCode 以不同归属出现多行（两位成员各点一份同款）时，每行都拿到全部金额。
**实测**（聚合/逐行两种官方返回形态都触发）：
```
items: X×1(m1) 25元, Y×1(m1) 10元, X×1(m2) 25元；官方总价 60 元
item_gross → [5000, 1000, 5000]   期望 [2500, 1000, 2500]
build_allocation → m1=3273分 m2=2727分   期望 m1=3500 m2=2500
```
**影响**：每人分摊被系统性错摊（实测每人偏差 2 元以上，随同码行数放大），直接违反「口径必须让用户能自己复算」（allocate.py 模块文档第 1 条）。整单合计因折扣反向配平恰好对得上，**错账不易被总数校验发现**。
**建议**：按 productCode 分桶后把官方小计**按行数量比例（或行顺序）拆分**回各行；同时补一条断言用例「同码多归属」进 test_engine。

### P0-2 「不要」硬约束漏判（自然语变体全部失效）
**位置**：`app/rules.py:143-169`（`expand_never`）、`rules.py:172-178`（`violates`）
**原因**：`expand_never` 只做**整词精确等值**匹配（`normalize(text) == normalize(group)` 或命中词表单词），用户输入任何变体（「辣的」「微辣」「不吃牛肉」「芝士奶酪」）就落入 unknown，仅按完整字符串做子串匹配；而商品名是「麦辣鸡腿堡」，不含「辣的」→ 不命中。
**实测**：
```
never=['辣']   → 命中「麦辣鸡腿堡」✔
never=['辣的'] → 不命中 ✘（keywords=['辣的']）
never=['微辣'] → 不命中 ✘
```
**影响**：前端占位文案就是自由输入（`web/app.js:479`「如：辣、牛肉」）。产品第一硬约束是「『不要』任何低价策略都不得突破」，此处是**静默漏判**——不报错、不排除，用户以为受保护实际没有。演示现场一旦有人输入「不吃辣」而非「辣」即翻车。
**建议**：双向包含匹配（`组词 in 输入 or 输入 in 组词`）+ 去后缀归一（的/类/味/制品）；对「不吃/不要/别吃」等前缀做剥离；命不中词表时至少把核心二字词做子串试配。并补测试用例覆盖变体输入。

### P0-3 失败结果被写入缓存，故障被放大固定时长
**位置**：`app/server.py:41-50`（`_cached`），影响 `load_menu`（180s）、`load_coupons`（300s）
**原因**：`_cached` 不区分结果成败，`loader()` 返回 `{"ok": False, error:{NETWORK/...}}` 也照样 `cache[key] = (now, value)`。
**实测**：失败后同 key 第二次请求直接复用失败结果，loader 只调用 1 次。
**影响**：网络抖动 1 秒 → 菜单/券「查询失败」被钉死 3~5 分钟；与 mcd_mcp 自身的降级回放叠加后，用户长时间看不到自愈。与「接口不可用时必须有明确反馈与**可恢复路径**」（规划 §12.2）冲突。
**建议**：仅缓存成功结果；失败最多以极短 TTL（3~5s）做防抖；或失败时立即穿透重试 loader。

## 三、P1 — 高

### P1-1 静态文件路径校验可被同级前缀目录绕过
**位置**：`app/server.py:275-287`（`_static`）
**原因**：`target.startswith(WEB_DIR)` 缺少路径分隔符收尾。`WEB_DIR=…/mmtx/web` 时，`/../web2/secret.txt` 归一化为 `…/mmtx/web2/secret.txt`，`startswith` 判定为真。
**实测**：`../web2/secret.txt` 通过校验（只要磁盘上真有 `web2/`、`web.bak/` 之类同级目录即被读出）。
**建议**：`os.path.normcase(target).startswith(os.path.normcase(WEB_DIR) + os.sep)`，或用 `os.path.commonpath([WEB_DIR, target]) == WEB_DIR`；再加 `os.path.realpath` 双保险。

### P1-2 beCode 校验后从未传给 MCP 接口（得来速模式不可用）
**位置**：`app/rules.py:285-286`（校验）vs `app/mcd_mcp.py:488-514, 574-590`（`query_menu` / `meal_detail` / `calculate_price` 的 arguments 均无 beCode）
**原因**：能力矩阵自述「到店自取(beType=1)不要传 beCode，传了会报错；得来速(beType=5)才需要」，校验层要求 beType=5 必须有 beCode，但适配层任何调用都没把它放进 arguments。
**影响**：得来速（beType=5）场景菜单/详情/核价大概率缺参失败；校验收集的 beCode 成了死数据。
**建议**：beType=5 时把 `beCode` 加入 query-meals / query-meal-detail / calculate-price 入参，其余 beType 严禁携带（能力矩阵说传了会报错）。

### P1-3 recalc 接口对 quantity 无边界校验
**位置**：`app/strategy.py:536-537`（`int(row.get("quantity") or 1)`）、`strategy.py:550`
**原因**：`or 1` 只把 0/None 兜成 1；**负数、超大整数**原样进 `_entry` 并送官方核价（`-5` 件、`10**9` 件）。ticket.py 有 `quantity <= 0 → 1` 的展示兜底，但入账/核价链路没有。
**影响**：恶意或误操作的请求可产生负金额条目、异常核价，甚至用超大数量压测官方接口。
**建议**：入口校验 `1 <= quantity <= 99`（并做 int 溢出防护），非法直接 400 + rejected 原因。

### P1-4 详情缓存键缺 store/beType 且永不过期
**位置**：`app/server.py:30`（`_detail_cache`）、`server.py:75-82`（`_fetch_details`）
**原因**：键只有 productCode。同款商品在不同门店/不同业态（到店 vs 外送）详情可能不同，却互相覆盖复用；且内存层**无 TTL**（注释说的 6 小时只是 mcd_mcp 磁盘层），进程不重启就一直增长、一直用旧数据。
**建议**：键改为 `store:beType:code`，写入时间戳并按 TTL（与磁盘一致 6h）+ 容量上限淘汰。

### P1-5 售罄刷新在外送场景失效（缓存失效参数写错）
**位置**：`app/server.py:93`：`drop("query-meals", {"storeCode": ..., "orderType": 1, "beType": ...})`
**原因**：真实调用参数是 `orderType=_order_type(be_type)`（`mcd_mcp.py:488-492`），beType=2（外送）时 orderType=2，而失效硬编码 1 → `_cache_path` 哈希不同 → 删不中文件，`invalidate` 静默返回 False。
**影响**：外送单「商品已售罄→刷新菜单重取」的补救链路失效，用户仍拿三张失败卡。
**建议**：抽出与 `query_menu` 共用的「构造 query-meals arguments」函数，失效与调用必须同源。

### P1-6 recalc 用券只传 couponId 不传 couponCode
**位置**：`app/strategy.py:538-540, 551-553`
**原因**：`_try_coupon`（strategy.py:283-285）与能力矩阵均表明 couponId + couponCode 需成对下发；手动调整（recalc）路径只透传了 `couponId`。
**影响**：用户改完餐品后，之前套用的券可能不生效或被官方拒（600012），界面只看到「试算被拒绝」。
**建议**：recalc 入参同时接收并透传 `couponCode`；缺失时明确提示「券信息不完整，本次未用券」。

## 四、P2 — 中

### P2-1 party_context 每次生成方案重复计算 3 遍（CPU 热点）
**位置**：`server.py:123`（_prepare 内）、`server.py:149`（api_plans 再算）、`strategy.py:369`（generate_plans 内又算）
**原因**：`party_context` → `resolve_wishes` → `match_wish` 对**每位成员×每条心愿×每件商品×(名称+组成)候选×同义词变体**跑 `difflib.SequenceMatcher`（rules.py:95-106）。8 人×3 档×3 条 × 100+ 商品时是 10⁵ 量级的 SequenceMatcher 调用，一次请求内跑 3 遍；售罄重试路径再翻倍。
**影响**：方案生成的纯 CPU 延迟可达秒级，叠加核价网络耗时后演示体验明显卡顿。
**建议**：`_prepare` 返回 ctx 后一路传递，`generate_plans` 收 ctx 参数不再重算；`similarity` 先做廉价短路（长度差、首字、子串）再进 difflib；必要时按 wish 做 LRU。

### P2-2 请求体无大小与合法性防护
**位置**：`app/server.py:264-273`（`_body`）
**原因**：`int(Content-Length)` 后直接 `read(length)`。① 无上限 → 超大 body 内存耗尽；② **负值**（如 `-1`）会让 socket file 的 `read(-1)` 一直读到对端关闭，工作线程被挂死；③ 非数字长度抛 ValueError 被误标成 `BAD_JSON`。
**建议**：校验 `0 <= length <= 1MB`，越界回 413/400；错误码区分「长度非法」与「JSON 非法」。

### P2-3 破坏性接口无鉴权/CSRF 防护
**位置**：`app/server.py:475-494`（POST `/api/cleanup`，scope=all 清空全部聚餐 + 缓存）
**原因**：服务默认绑 127.0.0.1，但浏览器里任意页面可用 `fetch(mode:'no-cors', content-type:'text/plain')` 发出 POST（`_body` 用 `json.loads` 解析，不看 Content-Type），无需 CORS 预检即可触发删除。
**建议**：要求自定义头（如 `X-Mmtx-Confirm`）迫使预检失败；或校验 `Origin` + 一次性确认 token；删除前返回待删清单由用户二次确认。

### P2-4 同一 party 读-改-写无并发保护
**位置**：`server.py:137-239`（api_plans / api_recalc / api_confirm / complete），`store.py:44-47`（锁只覆盖单次写盘）
**原因**：ThreadingHTTPServer 多线程下，两个请求对同一 party「读出→改→save」交错会互相覆盖（lost update），例如 confirm 与 plans 并发时 confirmedPlan 可能被旧状态盖掉。
**建议**：按 party_id 加细粒度锁（`dict[str, threading.Lock]`），或给 party 加版本号做乐观并发控制。

### P2-5 入参解析异常直接变 500
**位置**：`server.py:332`（beType）、`server.py:369`、`server.py:385`（memberCount）、`rules.py:285`（beType）等裸 `int(...)`
**原因**：`/api/menu?beType=abc`、`POST /api/party {"memberCount":"x"}` 等触发 ValueError，被 `except Exception` 兜成 500 SERVER。
**建议**：统一的入参归一化工具（int/float 解析失败→400 + 字段级错误），与 `validate_party` 的字段错误风格对齐。

### P2-6 非法 party id 返回 500，且 GET/POST 状态码不一致
**位置**：`store.py:32-36`（safe_id 抛 ValueError）；GET 走 `server.py:297-299` 的 `except Exception`→500；POST/PUT 走 `server.py:319-320` 的 `except ValueError`→400
**建议**：`safe_id` 失败在路由层统一映射为 404（资源不存在）或 400，避免 500。

### P2-7 「新」字导致新品误判，污染 C 方案
**位置**：`app/mcd_mcp.py:42`（`_NOVELTY_WORDS` 含单字「新」）、`app/rules.py:54`（`NOVELTY_HINTS` 同）
**原因**：子串匹配，「草莓**新**地」「**新**西兰风味」全被判 novelty。
**实测**：`_normalize_menu` 对「草莓新地」返回 `novelty=True`。
**影响**：C「一起尝点新」把常规甜品当尝鲜项；与事实优先原则冲突（这是推断出的伪事实）。
**建议**：删除单字「新」，只保留「上新/限时/新品/回归/新口味/新地」不适用的多字词，或只信 tags 不猜 name。

### P2-8 元→分换算两套口径不一致
**位置**：`app/rules.py:111-118`、`app/allocate.py:142`（float + `round`，银行家舍入）vs `app/mcd_mcp.py:116-130`（Decimal + ROUND_HALF_UP）
**原因**：内存约定「元字符串必须在适配层用 Decimal 转换」，但校验/预算层仍在用 float。`1.005` 之类边界值两端结果不同。
**建议**：把 `_yuan_to_cents` 提为公共工具，rules/allocate 复用；`check_budget` 的 `float(budget)*100` 同步替换。

### P2-9 无价格商品被静默丢弃
**位置**：`app/strategy.py:477`（`party_context` 过滤 `(priceCents or 0) > 0`）
**原因**：菜单价为空串时 `_yuan_to_cents` 返回 0 → 商品直接从候选池消失，且**无任何提示**；心愿匹配也看不到它，用户得到「本店当前菜单没有匹配」的误导结论。
**建议**：计数并在 `meta.warnings` 增加「N 款商品因未取到价格未纳入候选」，让用户知道是数据缺失而不是真没有。

## 六、性能观察（按影响排序）

1. **串行核价链**：`generate_plans` 内 B 基线 1 次 + 逐券 N 次 + A 撤回重算最多 k 次 + C 1~2 次；售罄重试整链 ×2；`calculate-price` 不缓存（正确）意味着每次都打到官方，单次超时上限 30s。最坏分钟级。
   → 建议：券试算只保留「命中商品数最多 / 标题含满减」的前 2~3 张；A/C 先用估价剪枝再动用官方核价；售罄重试只重算失败那一条而非全链。
2. **心愿匹配重复 3 遍 + difflib**（P2-1）：纯 CPU 热点，可先于网络优化。
3. **`prefetch_details` 8 路并发 + 6h 缓存**是正确的工程决策，保留。
4. **`/api/health` 双探活**（P3-13）在演示反复刷新时放大调用量。
5. `list_parties` 每次全量读目录内 JSON——演示规模无问题，超过百级再做索引。

## 七、安全性小结

| 项 | 状态 |
|---|---|
| 路径穿越（party id） | ✅ `safe_id` 白名单正则 |
| 路径穿越（静态文件） | ❌ 前缀比较可被同级目录绕过（P1-1） |
| 越权/鉴权 | ⚠️ 本机单用户模型可接受，但 destructive 接口缺 CSRF 防护（P2-3） |

| 敏感数据 | ✅ token 不落日志；accountHint 不外传 accountId；票根白名单式输出，金额/详址不回传 |
| 资源耗尽 | ❌ body 无上限、无请求并发限制（P2-2） |
| 供应链 | ✅ 零第三方依赖 |

## 八、测试盲区（建议补的回归用例）

1. `item_gross` / `build_allocation`：**同码多归属**、官方聚合行 vs 逐行两种形态（对应 P0-1）。
2. `expand_never`：变体输入「辣的/微辣/不吃牛肉/芝士奶酪」（对应 P0-2）。
3. `_cached`：失败结果不得长期缓存（对应 P0-3）。
4. `_static`：`/../web2/x`、`/../web.bak/x` 必须 404（对应 P1-1）。
5. `recalc_plan`：quantity=0/负数/超大值被拒（对应 P1-3）。
6. beType=5 时 invalidate 与 query_menu 的缓存键一致性（对应 P1-5）。
7. HTTP 层：非法 JSON / 超大 body / 非法 id 的状态码断言（对应 P2-2/2-5/2-6）。

## 九、建议修复顺序

1. **第一批（正确性底线）**：P0-1 分账、P0-2 忌口、P0-3 失败缓存 —— 都是「对外承诺被打破」级。
2. **第二批（模式可用）**：P1-2 beCode、P1-5 失效参数、P1-3 quantity、P1-6 couponCode —— 都是场景性功能缺口。
3. **第三批（加固）**：P1-1 静态路径、P2-2 body 防护、P2-3 cleanup CSRF、P2-4 并发锁。
4. **第四批（体验与维护）**：P2-1 重复计算、P2-7 新品误判、P2-8/2-9 口径统一，及 P3 清单。
