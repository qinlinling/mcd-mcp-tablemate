# P1 功能实现说明

对应规划：4.2「后续增强范围」与 5.7「再次相聚」。P1 在 P0 闭环稳定后才做，共四项：

| 编号 | 规划原文 | 本次实现 |
|---|---|---|
| P1-A | 经成员授权保存偏好，支持「原班人马，再吃一次」 | ✅ 逐人授权保存 → 一键带入新聚餐 → **强制重新查菜单、重新核价** |
| P1-B | 添加合照、每人一句话和下次约定 | ✅ 三项都可选填，落库到 `party.ticketExtras`，刷新不丢 |
| P1-C | 增加多种票根版式和适配不同分享渠道的尺寸 | ✅ 竖版 / 方图 / 竖屏三版式，1080 宽导出 |
| P1-D | 用户主动标记聚餐已完成后，关联真实订单 | ✅ **只读**关联（`order-list` / `query-order`），并做三项事实核对 |

**明确不做**：`create-order` 下单、`auto-bind-coupons` 领券。作品从设计上不替用户下单——
订单必须由用户自己在麦当劳 App/小程序完成，再回来关联。这条边界写在代码注释、界面文案和本文档里。

## 一、P1-A 偏好授权与「原班人马，再吃一次」

### 1.1 授权语义（规划 §11「授权先于保存」）

- **逐人授权**：前端每名成员一个「同意保存我的口味偏好」勾选框，**默认不勾选**；
  只有勾了的人才会进库，其余成员一个字都不写。
- **一个人都没授权**时服务端直接拒绝（`NO_CONSENT`），不生成空组。
- **最小化**：只存 `昵称 + 必须要 + 最好有 + 不要`。
  **不存个人预算**（财务信息、且每次聚餐本就会变）、不存订单、不存金额、不存门店。
- **可撤回**：偏好组可单独删除（`DELETE /api/preferences/{gid}`）；「清除本地数据」选 `all` 时会一并清除，
  选 `parties` 时**不动**偏好——用户只想清聚餐记录，不该顺带删掉授权过的口味。

### 1.2 数据流

```
第 5 步（确认方案后）
  └─ 勾选成员 → POST /api/party/{id}/preferences
        └─ app/preferences.build_group()  逐人过滤 → .data/preferences/{gid}.json
第 1 步（下次）
  └─ GET /api/preferences  → 卡片「上次这群人」
        └─ 选门店 + 填预算 → POST /api/preferences/{gid}/revisit
              └─ preferences.party_from_group() → 新的 draft 聚餐（plans=[] / dataTime=null）
                    └─ 必须重新生成方案：菜单与价格一律重查（不沿用旧核价）
```

### 1.3 关键边界

| 场景 | 处理 |
|---|---|
| 偏好组只有 1—2 人授权 | 自动补齐到 3 人下限（空昵称位），返回 `needsFill: true`，让用户在第二步填写，而不是抛「人数不合法」 |
| 再聚时不选门店 / 不填预算 | 400 + 明确文案「再聚也要先选门店：菜单和价格必须按当前门店重新查」 |
| 再聚后直接去票根 | 不允许：`confirmedPlan` 为空 → `NOT_CONFIRMED` |
| 偏好的菜已下架 | 生成方案时按当前菜单匹配，匹配不到如实写「本店当前菜单没有匹配『x』的餐品」 |
| 偏好组的标题过长 | 截断到 27 字再拼「·再聚」，避免超过 30 字上限 |
| 旧聚餐已确认 | 保存偏好要求 `confirmedPlan` 存在，否则拒绝（没有确认方案就没有可信的心愿来源） |

## 二、P1-B 票根增强：合照 / 每人一句话 / 下次约定

### 2.1 字段与校验

| 字段 | 类型 | 校验 | 默认 |
|---|---|---|---|
| `photo` | dataURL 字符串 | 仅 `data:image/jpeg|png|webp;base64,`；长度 ≤600KB；拒绝 http 外链（离线导出会空白）与 svg（可带脚本） | 不填则不出现 |
| `notes` | `{memberId: text}` → 输出 `[{member, note}]` | 只接受聚餐内存在的成员；每条 ≤24 字；≤8 条 | 不填则不出现 |
| `nextMeet` | 字符串 | ≤40 字 | 不填则不出现 |

字段开关与 P0 一致：`fieldsVisible` 里为 `false` 的字段**整块不渲染**（不是 `display:none`），
所以用户取消勾选「合照」时，导出的图里不会留白块。

### 2.2 落库

`POST /api/party/{id}/ticket` 会把本次的 `visibleFields / nicknames / themeLine / photo / notes / nextMeet`
合并进 `party.ticketExtras` 并保存，`GET /api/party/{id}` 会带回。
这样刷新页面后照片与句子不会「看起来保存了、其实丢了」。

### 2.3 隐私

- 照片是用户自己上传的，**只有主动上传才存在**；不上传就没有任何默认图片。
- 票根仍然不含：订单号、门店详址、个人预算、个人分摊、实际支付金额。

## 三、P1-C 多票根版式与分享尺寸

| 版式 | 画布 | 适用 | 排版取舍 |
|---|---|---|---|
| `portrait` 竖版 | 1080 × 自适应 | 微信聊天、朋友群 | 完整信息优先，餐品最多 3 件 |
| `square` 方图 | 1080 × 1080 | 朋友圈、小红书方图 | 压缩留白、字号略降，餐品最多 3 件 |
| `story` 竖屏 | 1080 × 1920 | 状态/快拍类 9:16 | 照片可占更大高度、底部留白更多 |

实测尺寸（真实 canvas：jsdom + `canvas` 包，`tests/export_sizes.mjs`）：

| 版式 | 实测输出 | 文件大小 |
|---|---|---|
| portrait（含照片+句子） | 1080 × 2382 | 258 KB |
| square | 1080 × 1080 | 155 KB |
| story | 1080 × 1920 | 232 KB |
| square（无照片/无句子） | 1080 × 1080 | — |
| portrait（传了非法外链照片，被忽略） | 1080 × 1868 | — |

### 预览与成品的关系（避免「预览 ≠ 导出」的误解）

- **页面预览**走 DOM，按屏幕宽度等比缩放，**并按所选版式重排**（方图/竖屏为双栏结构）。
  这样做的好处是文字可选、可截图、不消耗画布性能。
- **像素尺寸只由导出保证**。界面上的尺寸小字写的是真实导出值。
- 另提供 **「查看导出效果」** 按钮：按需调用 `exportPNG` 生成与下载**完全一致**的 1080 图，
  在弹层里展示（Esc / 点遮罩 / 关闭按钮均可退出）。
  刻意不把它挂在输入回路上——每次输入都重画 2160px 画布既慢又没有意义。

## 四、P1-D 关联真实订单（只读）

### 4.1 为什么是只读

规划 4.2 写的是「在二次确认后创建订单」，但那意味着真的花钱。
本作品坚持 P0 的只读边界：**只调用 `order-list` / `query-order`**，
用户自己在麦当劳 App 下单完成后，回来把订单关联到这次聚餐。

### 4.2 三项事实核对（不替用户判真伪）

关联时只呈现可核对的事实，不给出「是不是同一顿」的结论：

| 核对项 | 判断方式 | 不一致时的提示 |
|---|---|---|
| 门店是否一致 | `order.storeCode == party.store.storeCode` | 「该订单来自『X』，与本次聚餐的门店不一致」 |
| 时间是否合理 | 订单下单时间 ≥ 聚餐创建时间 | 「该订单的下单时间早于这次聚餐的创建时间，可能不是同一顿」 |
| 餐品是否重合 | 已确认方案与订单的 `productCode` 交集数 | 「订单餐品与已确认方案没有任何重合，请确认是否关联错了订单」 |

不通过**不拦截**——跨门店、提前点好都真实存在，系统只提示，由用户勾选确认后继续。
时间字段解析失败时返回 `timeOk: null`（「不知道」），不猜。

### 4.3 脱敏

- 订单号只存在本地 `.data/` 与 `party.linkedOrder` 里；
- 界面只显示**后 4 位**（「订单 …0019」）；
- 票根里连后 4 位都不出现，只显示状态「已完成」；
- 回归用例显式断言：把真实订单号塞进 party 后，`build_ticket` 的输出里搜索不到它。

### 6.3 手工验收（演示前必过）

1. 保存偏好时只勾 2 人 → 检查 `.data/preferences/*.json` 里确实只有 2 人，且没有 `budget` 字段。
2. 用该组再聚 → 第 2 步应出现 2 位已填 + 1 位待填；补齐后生成方案，价格必须与上次不同（重新核价）。
3. 票根上传一张 >600KB 的照片 → 前端应自动压缩后成功，或给出明确失败提示。
4. 票根取消勾选「合照」→ 预览与导出都没有照片，且没有留白。
5. 关联订单 → 当前账号订单来自另一家门店，应出现 3 条黄色警告；界面订单号只显示后 4 位。
6. 刷新页面 → 照片/句子/约定仍在（来自 `ticketExtras`）。
7. 设置抽屉删除偏好组 → 第 1 步卡片同步消失。
8. 「查看导出效果」→ 弹层里应出现 1080 宽的图，切换版式后再点，标题与图片尺寸同步变化。

## 七、已知限制与取舍

| # | 限制 | 为什么这样选 |
|---|---|---|
| 1 | 不创建订单（只读关联） | 会真实扣款，越出「只读优先」；见 `实现与规划对照.md` D-13 |
| 2 | 照片只接受 dataURL，不收外链 | 票根要能离线导出；外链图在断网/防盗链时会变空白，且 svg 可带脚本 |
| 3 | 照片上限 600KB（前端先压到长边 1200） | 与后端 `MAX_BODY=1MB` 留出余量；票根是社交分享物，不需要原图 |
| 4 | 偏好不复用个人预算 | 财务信息 + 每次聚餐预算本就不同；复用价值低、风险高 |
| 5 | 订单某项核对失败不拦截 | 跨门店、提前点好都真实存在；系统给事实，不替用户判真伪 |
| 6 | DOM 预览不是 1080 等比 | 屏宽限制下文字要可读；精确效果由「查看导出效果」与下载保证 |
