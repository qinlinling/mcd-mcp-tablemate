# 主流程、异常流程与三类方案规则

对应规划：阶段 1 交付（第 7 节门槛：主流程可走通，每个输入和输出有明确来源）、
第 5.2 节三类方案、第 5.4 节分账口径、第 8.2 节 B02—B05。

## 一、主流程（五步）

```
① 创建聚餐            ② 收集心愿              ③ 三案对比
事由/人数/门店/预算  →  逐位填三档心愿      →  三个策略各出一桌
（真实门店查询）        自动解析到菜单项        官方核价 + 心愿处理 + 取舍说明
        │                      │                      │
        └──────────────────────┴──────────────────────┘
                               ↓
                    ④ 调整与确认                ⑤ 同桌票根
                 改餐品 → 重新核价          字段勾选/昵称改写
                 确认 = 保存为方案            预览 → 下载 PNG
```

数据来源标注（每个输出的出处）：

| 输出 | 来源 | 缺失时 |
|---|---|---|
| 门店列表 / 门店编号 | `query-nearby-stores` | 提示换关键词，不生成方案 |
| 餐品名、价格、图片、分类 | `query-meals`（`currentPrice` 元 → 内部转分） | 方案不生成 |
| 套餐组成（用于忌口校验） | `query-meal-detail`（各 round 的默认 choice） | 忌口退回「仅按名称校验」并写入 warnings |
| 可用券及适用商品 | `query-store-coupons` | 跳过用券，方案照常生成 |
| 整单金额、优惠额、分项金额 | `calculate-price`（单位：分） | 该方案标记「核价失败，不可选」 |
| 心愿解析结果 | 本地规则（序列相似度 + 同义词表） | 报「未匹配」，不替用户假设 |
| 分账 | 本地规则（`allocate.py`），仅用官方分项金额 | 退回「单价×数量」并标注口径差异 |

## 二、三类方案规则（可测试的策略定义）

三套方案共用同一套硬约束与价格来源，差别只在「目标函数」与「是否加配」。

| 维度 | A 人人有期待 | B 整单更划算 | C 一起尝点新 |
|---|---|---|---|
| 首要目标 | 每位成员的核心心愿优先 | 满足硬约束后压低整单 | 保留核心心愿，加入探索项 |
| 每人主力单品 | 心愿匹配档内、**同时能顺带满足「最好有」**、优先单品而非套餐 | 心愿匹配档内**最便宜**，优先单品 | 同 A |
| 配餐 | 每人最多补 1 件，且必须能对上他的「最好有」，并受共同预算约束 | 不加配餐 | 不加个人配餐 |
| 探索项 | 无 | 无 | 最多 2 件，**共享**，必须是新品/限时/回归，且避开所有人忌口 |
| 优惠券 | 不叠加（避免三案被优惠同化），文案指向 B | 逐张试算，**仅当官方实付更低才采用** | 同 A |
| 必须说明的取舍 | 比最省方案多花多少、换来什么；哪些「最好有」被舍弃 | 哪条「必须要」为压价未满足；券为何没用上 | 新增了什么、贵了多少、预算剩多少 |

**收敛处理**：若两套或多套方案的「餐品 + 数量」完全一致，系统给这几套标注
`convergedWith`，并在取舍里说明「当前菜单与硬约束下没有可产生差异的替代组合」。
禁止为了形式差异微调结果。

**为什么每个人的主力单品都从「心愿匹配档」里挑**：这是「解释优先于分数」的落地——
用户能对着清单说「这件是我的」。匹配档 = 相似度 ≥ 最高分 × 0.85 的候选，
避免「麦辣鸡翅」蹭到「麦辣鸡腿堡」。

## 三、分账口径（可复算）

1. **归属项**：每份餐品挂在某人名下，金额全额计入该人。
2. **共享项**（探索项、手动加的无归属餐品）：按在场人数均摊，除不尽的 1 分钱从成员 1 开始逐个补足。
3. **优惠**：按各人「归属金额 + 共享分摊」占比分摊，用最大余额法补平分位差。
4. 不变量：`Σ 每人应付 == 官方核价实付总额`。前端分账表底部实时校验并显示「一致 / 不一致」。
5. 优惠造成的差额**不会凭空消失，也不会由某一个人兜底**——它按占比回到每个人身上。

示例（实测，A 方案）：整单 ¥113.50 = 小北 36.00 + 阿岚 27.00 + 大可 35.00 + 糖糖 15.50。

## 四、异常流程与降级口径

| 场景 | 系统行为 | 用户可恢复路径 |
|---|---|---|
| 门店/关键词查不到 | 提示「换个商圈关键词或城市」 | 改关键词重查 |
| 菜单接口失败 | 中断方案生成并显示错误原因；不展示任何价格 | 重试 / 换门店 |
| 某餐品无详情（缺套餐组成） | 忌口仅按名称校验，方案 `warnings` 明说 | 换餐品 |
| 券不适配本单商品 | 取舍里写「券仅适用于 X，本单未包含，未使用」 | 手动加该商品后复算 |
| 券试算被官方拒绝（600012） | 记录「试算被官方拒绝：促销规则不支持该商品」 | 换券/换商品 |
| 官方核价失败 | 方案 `pricing.ok=false`，金额显示「未知」，按钮变「核价失败，不可选」 | 重新生成方案 |
| 菜单里有、门店已售罄（`60006`） | 三案都因售罄失败时，自动丢弃菜单缓存→重取→重算一次，`meta.menuRefreshed=true` 并在界面提示；仍失败才展示失败卡 | 自动重试一次，无需用户操作 |
| 断网 / 超时 | 有缓存 → 「离线回放·非实时」横幅 + 原始时点；无缓存 → 「不可用」 | 恢复网络后重试 |
| 改动餐品后 | 旧金额立即作废，显示「核价中…」，返回新结果才替换 | — |
| 修改心愿/门店/预算 | 聚餐状态回退 `draft`，已确认方案与旧核价一并作废 | 重新生成方案 |
| 归属人不存在 | 该餐品按共享处理，并写 warnings（钱不会丢） | 修正归属 |
| 把辣味餐品挂给不吃辣的人 | 复算拒绝该条目并列出原因 | 换人/换品 |

## 五、手动调整与复算（B05）

1. 第 4 步可增删餐品（按分类分组 + 搜索）、改数量、改归属；
2. 每次改动触发 `POST /api/party/{id}/recalc`，重新走 `calculate-price`；
3. 复算会重跑：硬约束校验 → 分账 → 心愿结果 → 取舍文案；
4. 被硬约束拒绝的条目不会静默丢弃，而是列在 warnings 里；
5. 确认后的方案是**快照**，票根只读该快照，不读实时菜单。

## 六、状态机

```
draft ──生成方案──→ planned ──确认──→ confirmed ──主动标记完成──→ completed
  ↑                    │                  │
  └────改心愿/门店/预算─┴──────────────────┘   （旧核价作废，回到 draft）
```
