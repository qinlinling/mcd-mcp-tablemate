### 2.4 产品原则（规划第 11 节）在代码中的落点

| 原则 | 落点 |
|---|---|
| 实用先于传播 | 票根只有一处入口（步骤 5），无动画特效；先保证点餐闭环 |
| 事实先于文案 | 所有价格来自 `calculate-price`；票根字段全部可溯源到 party/plan |
| 解释先于分数 | 无任何评分字段；`tradeoffs` 每条都含具体金额或具体餐品 |
| 授权先于保存 | 票根字段可勾选、昵称可改写；不保存偏好；`/api/cleanup` 一键清 |
| 确认先于变更 | 无下单/领券；标记完成需二次确认弹窗 |
| 降级先于编造 | `mcd_mcp._degrade`：有快照标 `replay` + 原始时点，无快照标 `unavailable` |
| MVP 先于扩展 | P1/P2 全部未实现，README 与演示脚本都明说「这一版没有假装做完」 |

## 三、偏离规划之处及原因

> 判定口径：凡是「规划写了但没做」「规划没写但做了」「规划写了但做的方式不同」都列进来。

### D-1｜从「只做规划」推进到「完成 MVP 实现」

- **规划原文**：第 13 节「当前只完成规划，不进入具体编码」；第 7 节「当前位于阶段 0」。
- **实际**：完成阶段 0—3，并把阶段 4/5 的文档补齐。
- **原因**：你的指令明确要求按规划实现。为避免「跳过验证直接开发」，
  阶段 1/2 的产物（规则文档、能力矩阵、联调记录）先写、后编码，且编码中所有接口行为都以实测为准。
- **影响**：无功能风险；规划文档的「当前阶段」表述已过时，建议把第 13 节状态更新为阶段 5。

### D-2｜技术选型为「Python 标准库 + 原生前端」

- **规划原文**：未指定技术栈（只指定「MCP 真实数据」「本地清理」「可复现演示」）。
- **实际**：后端 `http.server.ThreadingHTTPServer` + `urllib`，前端原生 HTML/CSS/JS，零第三方依赖、无构建。
- **原因**：仓库里已有 `mcd-mcp/mcd.py`（纯标准库）验证过 token 与 JSON-RPC 细节；现场演示最怕装依赖。
- **代价**：没有 ORM、没有前端框架，复杂交互要手写（已用分区 + 单 `state` 对象控制复杂度）。

### D-3｜取餐方式：到店自取 + 得来速已支持，外送/团餐未开放

- **规划原文**：4.1-1「填写聚餐事由、人数、**门店或取餐条件**及共同预算」。
- **实际**：`beType=1`（到店自取）与 `beType=5`（得来速）均已打通；麦乐送（2）、企业团餐（6）未开放。
- **变化过程**：最初只开到店自取，因为 `query-nearby-stores(beType=1)` 不返回 `beCode`；
  后来在代码审查轮次里补上了 `beCode` 全链路透传（`mcd_mcp.menu_arguments`），
  实测 `beType=5` 的门店列表**会**返回 `beCode`，菜单 125 项、三套方案核价全部成功（2026-10-25 17:33）。
- **仍未开放**：外送/团餐需要 `delivery-query-stores` 与不同的 `orderType`，本轮未验证，按规划 9.1 不写入承诺。
- **影响**：取餐方式覆盖 2/4；界面只给用户这两个选项，其余不出现，不存在「点了报错」的死路。
- **恢复路径**：验证 `delivery-query-stores` 后，把 `beType=2/6` 接进 `menu_arguments` 即可（已预留分支）。

### D-4｜「已完成」状态只做标记，未关联真实订单

- **规划原文**：4.1-8 要求票根标明「计划中」或「已完成」；4.2（P1）才是「标记已完成后**关联真实订单**」。
- **实际**：实现了「用户主动标记已完成 / 取消标记」（二次确认），但不关联任何订单。
- **原因**：P0 必须能表达两种状态，而订单能力属 P1 且未验证。取二者交集：状态可表达，订单不碰。
- **影响**：票根上不会有订单号、支付金额；「已完成」仅代表用户自己确认吃过了。

### D-5｜「不要」的作用范围细化为「本人餐品 + 共享餐品」

- **规划原文**：5.1「『不要』属于硬约束，不能为了低价被自动突破」（未定义作用范围）。
- **实际**：个人餐品只校验归属人的忌口；共享餐品校验全桌忌口并集。
- **原因**：这是回归测试暴露的真实缺陷（见测试报告缺陷 1）。若按「整桌忌口」处理，
  阿岚不吃辣会让小北的「必须麦辣鸡腿堡」被判为不可满足——既不合常识，也违背 5.1「让不同成员的心愿被看见」。
- **影响**：行为比字面理解更宽松但更正确；已在规则文档 §边界口径 1 固化。

### D-6｜新增「心愿同义词表」（规划未提及）

- **规划原文**：5.1「系统不擅自推测未填写的偏好」。
- **实际**：内置一张极短的同义词表（如 鸡块 → 麦乐鸡、可乐 → 可口可乐），用于把口语映射到菜单命名；
  匹配结果会展示给用户，未收录词按字面匹配并在 warnings 提示「仅按字面匹配」。
- **原因**：不映射就会出现「用户说鸡块、菜单叫麦乐鸡 → 判定无匹配」，这是可用性缺陷而非谨慎。
- **边界**：同义词只做「叫法」映射，不推断口味偏好、不新增用户没提过的需求。表长度控制在 12 条以内，避免变成黑箱。

### D-7｜票根版式与导出尺寸（原为 P1 留空，本轮已补齐）

- **规划原文**：4.2（P1）「增加多种票根版式和适配不同分享渠道的尺寸」。
- **实际**：竖版（宽 1080、高随内容）/ 方图（1080×1080）/ 竖屏（1080×1920）三版式，已用真实 canvas 验证像素。
- **补充设计**：DOM 预览按屏宽等比缩放并**按版式重排**（文字可选），像素尺寸由导出保证；
  另提供「查看导出效果」按钮，按需生成与下载完全一致的 1080 图，避免「预览≠成品」的误解。

### D-8｜离线回放由「准备材料」变为「运行时自动降级」

- **规划原文**：第 10 节风险表「准备脱敏回放和异常说明，同时明确标注演示数据来源」。
- **实际**：`mcd_mcp` 自动读写缓存；断网时返回 `source=replay` + 原始 `dataTime`，前端显示黄色横幅「离线回放·非实时」。
- **原因**：比人工准备回放材料更可靠，且不会忘标来源；同时满足「不冒充实时结果」。
- **验证**：`tests/test_degrade.py::test_replay_keeps_original_datatime_and_flags_source`。

### D-9｜E03 目标用户可用性测试未执行

- **规划原文**：E03「进行目标用户可用性测试并修正主流程」；12.6「至少完成一轮目标多人场景测试」。
- **实际**：用 5 组规则级场景（3/4/6/8 人）+ 1 套端到端标准场景替代，**没有真人测试**。
- **原因**：本次执行环境内没有真实用户；伪造「用户测试记录」会违背「事实先于文案」。
- **影响**：这一条在测试报告中明确标为「⚠️ 未做」，不计入已通过项。

### D-10｜新增「填入标准演示场景」按钮（规划外）

- **原因**：演示与验收需要固定输入；按钮只填表单，不伪造任何门店、菜单或价格。
- **风险控制**：填完后仍要真实查门店、真实核价，任何一步失败都会如实报错。

### D-11｜数据存储用本地 JSON 文件，未接数据库

- **规划原文**：未指定；但 4.1-9 要求「本地数据清理入口」，12.5 要求「用户可清除」。
- **原因**：文件即数据，删文件即删除，最容易向用户解释「清理到底清了什么」。

### D-12｜未实现领券（`auto-bind-coupons`）

- **规划原文**：11 节「任何领券、下单、支付或其他变更类操作均需独立确认」；P0 未要求领券。
- **实际**：只查询可用券并用官方核价验证「用券后是否更便宜」，不领券。
- **影响**：账号里未领取的券不会被本作品领取；演示时若券未领取，方案会如实显示「无可用优惠」。

---

### D-13｜不做「二次确认后创建订单」，改为只读关联

- **规划原文**：4.2「在二次确认后创建订单，并提供清晰的订单状态反馈」。
- **实际**：**不调用** `create-order`。改为让用户在麦当劳 App/小程序自行下单后，
  用 `order-list` / `query-order` 只读关联，并给出门店/时间/餐品三项核对。
- **原因**：创建订单会真实扣款，属于不可撤回的外部变更，超出「只读优先」的产品承诺；
  且 P0 已明确「MVP 不默认执行实际下单或支付」。
- **代价**：用户需要多一步「自己去下单」；换来的是任何演示都不会误花用户的钱。
- **恢复路径**：若后续要做，必须独立开关 + 二次确认 + 明确的金额与门店回显，且不能与票根生成绑定。

## 四、如果继续做，下一步优先级

1. **真人可用性测试**（E03）：找 1 组 3—4 人真实聚餐跑一遍，重点看第 2 步填写是否真的比群里问更省事。
2. **视觉定稿核对**：真实浏览器 1440 / 390 两档截图，检查票根三版式的文字溢出与撕线锯齿。
3. **D-3 取餐方式扩展**：验证 `delivery-query-stores` 的 `beCode` 后开放外送/团餐。
4. **HTTP 层自动化**：把错误码/并发/CSRF 的手工 curl 换成进程内临时 server 的用例。
5. **（可选）订单闭环**：若要真下单，按 D-13 的恢复路径单独设计，不与票根耦合。
