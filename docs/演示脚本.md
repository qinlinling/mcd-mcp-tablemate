# 演示脚本（30 秒概念 + 3 分钟完整场景）

对应规划：E04、12.6。

## 一、30 秒版（评委/路人）

> 多人聚餐最麻烦的不是找便宜，是「谁想吃什么、谁不能吃什么、预算够不够」来回问。
> 麦麦同席让每人填三档心愿：必须要、最好有、不要。
> 其中「不要」是硬约束，任何省钱策略都不会去碰它。
> 系统用**真实门店菜单和官方核价**给出三张不同的桌子：
> 一张照顾每个人的心愿，一张把整单压到最省，一张留一点尝新的余地。
> 每张桌子都告诉你「谁的心愿被满足了、谁被调整了、为什么」。
> 确认之后，一键变成一张**同桌食光票根**——可以撕下来分享的那种。
> 先把这顿饭点好，再把这次相聚留下。

要点提示：**不说「最省」「最公平」「最健康」**；说「官方核价」「硬约束」「可解释的取舍」。

## 二、3 分钟完整演示

### 准备（演示前 2 分钟）

```bash
cd mmtx && python run.py
# 浏览器打开 http://127.0.0.1:8848
# 建议：演示前先点一次「填入标准演示场景 → 查门店」，让菜单进缓存，现场更顺
```

### 第 0 步｜定位（20s）

一句话：这不是又一个省钱比价工具，是**一群人的一次协商 + 一张可以留存的票根**。
顶部数据时点条先亮出来：「数据时点 2026-10-25 14:19，官方核价」——先立事实，再讲故事。

### 第 1 步｜创建聚餐（20s）

> P1 起「取餐方式」支持到店自取与得来速（得来速要求门店返回 beCode，已实测三案可核价）；外送与团餐仍未开放。

点「填入标准演示场景」，表单自动填好：周五项目庆功 / 4 人 / 上海 人民广场 / 共同预算 200。
点「查找门店」→ 选第一家（华旭国际大厦餐厅，144m，支持预约）。

> 讲点：门店、菜单、价格都不是我编的，全是官方接口；页面上这个时点就是证据。

### 第 2 步｜成员心愿（45s）

座位卡逐位填写，每人三档：

- 小北：必须 麦辣鸡腿堡；最好有 薯条
- 阿岚：必须 鸡块；不要 **辣**
- 大可：必须 巨无霸；最好有 可乐
- 糖糖：必须 麦旋风；不要 牛肉

> 讲点 1：「鸡块」在本店菜单里叫「麦乐鸡」，系统按同义词匹配，并把匹配结果展示给你确认，不替你拍板。
> 讲点 2：阿岚不吃辣，但这不会导致小北不能点麦辣——**忌口约束的是本人吃的东西**，共享餐才需要避开所有人。

### 第 3 步｜三案对比（60s，核心）

点「生成三套方案」（冷启动约 5s，命中缓存约 2s）。

依次讲三张卡，每张只看三件事：**总额、谁的心愿满足了、代价是什么**。

| 讲什么 | 台词 |
|---|---|
| 人人有期待 ¥113.50 | 「4 条必须要全部满足，还补了薯条、玉米杯、可乐。比最省的那套多花 ¥36——这 ¥36 买的是每个人的期待。」 |
| 整单更划算 ¥77.50 | 「同样守住所有『不要』，只保证必须要，不补配餐。券我试算了，账号里那张券只适用于龙焰鸡腿堡两件套，本单没有这件商品，所以如实说没用上，而不是假装抵扣。」 |
| 一起尝点新 ¥93.50 | 「在必备项基础上共享两份新品：灰焰圆筒和马苏里拉芝士条。官方核价还给了 ¥4 优惠，实付 ¥93.50。」 |

然后指一张卡的「取舍说明」：**每一句都能对着清单核对**，没有「公平分 87 分」这种算不出来的东西。
如果本次运行三套刚好一致，界面会显示「与 X 方案策略收敛」并说明原因——不制造假差异。

### 第 4 步｜调整与确认（30s）

点某张卡「选这套，去调整」：

1. 从右侧菜单加一份可乐 → 金额先变「核价中…」，再刷新成新金额。
   > 讲点：改动之后旧价格立即作废，一定重新问官方，不拿缓存糊弄。
2. 看分账表：每人「归属 + 共享分摊 − 优惠分摊 = 应付」，底部一行实时校验
   「分账合计 ¥xx = 整单 ¥xx，一致」。
   > 讲点：钱不会凭空消失，优惠按占比回到每个人身上。
3. 点「确认这套方案」→ 提示「仅保存为聚餐方案，未下单、未支付、未领券」。

### 第 5 步｜同桌票根（25s）

自动跳到票根页：

1. 左侧是带撕裂线的纸质票根：事由、日期、四位同桌、三件代表餐品、被满足的小心愿、一句手写短句。
2. 右侧可勾选展示字段、逐个改昵称、改主题句。
   > 讲点：默认隐藏订单号、门店详址、个人预算、个人分摊、实际支付金额——发起人没有替别人公开这些的权利。
3. 点「下载图片」拿到 1080 宽的 PNG，可直接发群里。
4. 想标「已完成」需要再确认一次；不勾就一直是「计划中」。
   > 讲点：绝不会把「计划」说成「已消费」。

### 收尾（15s）

> 这条闭环是：聚前一起选 → 聚后一起晒 → 下次再相聚。
> 下次再聚（复用偏好、重新核价）和接真实订单都在 P1，这一版**没有**假装做完。

## 三、被追问时的标准答法

| 问题 | 回答 |
|---|---|
| 和别的省钱工具有什么不同？ | 省钱只影响总价；这里要解决的是「一群人的偏好怎么被看见」。三档心愿 + 取舍解释 + 关系型票根，这是差异点 |
| 价格可信吗？ | 每一分钱都来自 `calculate-price`，页面带数据时点和 traceId；核价失败就显示未知，不给估算 |
| 三套方案会不会是同一个？ | 可能会。菜单单调时策略会收敛，我们如实标注原因，不硬凑差异 |
| 不吃辣会不会误判？ | 靠「餐品名 + 套餐组成名」关键词匹配，没有官方辣度字段。所以我们**不做**过敏原安全承诺，未收录词会提示「仅按字面匹配」 |
| 会不会偷偷下单？ | 不会。代码里没有任何下单/领券调用；确认只写本地文件 |
| **为什么不做真实下单？** | 三条理由：① 下单会真实扣款、不可撤回，与「只读优先」的产品承诺冲突；② 本作品的差异化是「协商 + 票根」，闭环缺口用「只读关联真实订单」补上；③ 头部作品里也不是人人都做——抽查 Top60 的 48 个 README，15 个提到 `create-order`，其中约 9—10 个做成「确认后真实下单」，另有 4 个明确写「不调用 create-order」（如 mcd-budget-planner、mcd-buddy）。我们选择后者，并在文档里写明取舍 |
| 那用户怎么完成闭环？ | 用户在麦当劳 App/小程序自行下单 → 回来「关联我的麦当劳订单」→ 系统做门店/时间/餐品三项核对 → 票根变成「已完成」。订单号只在本地，界面只显示后 4 位 |
| 断网怎么办？ | 有历史快照就标「离线回放·非实时」并给出原始时点；没有就显示不可用。绝不编价格 |
