# 设计决策记录

本文记录实现过程中**影响产品行为的取舍**，每条都写清「为什么这么定」以及可选方案被放弃的原因。
评审若要判断「这不是随手拼的」，看这份比看代码更快。

---

## D-01 技术选型：纯标准库 + 原生前端

**决定**：后端 Python 3 标准库（`http.server` + `urllib`），前端原生 HTML/CSS/JS，零第三方依赖、无构建。
**原因**：现场演示最怕「装依赖 / 构建失败」；且 MCP 只需 HTTP JSON-RPC，框架带不来额外价值。
**代价**：没有 ORM 与组件框架，复杂交互要手写（用单一 state 对象 + 分区渲染控制复杂度）。

## D-02 MCP 链路的三条实测结论（决定了很多后续设计）

1. **菜单列表 ≠ 可核价集合**：券适用商品可能不在 `query-meals` 返回里，但 `calculate-price` 仍能核价。
   → 选品只从菜单取，券抵扣只在「商品在菜单内 + 券匹配」时启用，避免推荐一个用户点不到的商品。
2. **券不适用是业务结论**：`success=false / code=600012`，不是故障。
   → 单独归类，`source` 保持 `live`，文案写「券仅适用于 X，本单未包含」。
3. **菜单会「有货变无货」**：缓存里的商品下架后，官方核价整单拒绝（`60006`）。
   → 菜单 TTL 120s；核价因售罄全失败时丢弃菜单缓存重取并重算一次（`meta.menuRefreshed`），断网类失败不触发。

## D-03 忌口（「不要」）的校验口径

按关键词在「餐品名 + 套餐组成名」上匹配；`NEVER_GROUPS` 维护同义词组（辣→辣/辛/椒麻…）。
未收录的自由词按原文兜底，并在 warnings 标注「仅按字面匹配」——**不谎称已验证**。
拿不到套餐组成时只按名称校验，同样如实标注。**不做过敏原安全承诺**（官方无结构化过敏原字段）。

## D-04 忌口的作用范围：本人 + 共享（曾犯过的错）

早期把「不要」当成整桌约束，导致「阿岚不吃辣 → 小北不能点麦辣鸡腿堡」，既不合常识，
也违背「让不同成员的心愿被看见」。**最终口径**：个人餐品只校验归属人忌口；共享餐品校验全桌并集。
这条是回归测试抓出来的，修复过程见 `审查问题核实与修复记录.md`。

## D-05 心愿匹配：difflib + 同义词 + 同档过滤

字符二元组 Jaccard 会把「麦辣鸡腿堡」匹配到「麦辣鸡翅」（0.4 恰好过线）。
改为 `difflib.SequenceMatcher` 比例 + 包含式长度折算，阈值 0.55，只保留与最高分同档（×0.85）的候选，
套餐项 ×0.85 降权；另加口语同义词（鸡块→麦乐鸡 等）。匹配结果会展示给用户，不替用户拍板。

## D-06 三类方案是三种目标函数，不是同一算法换文案

| 方案 | 目标 | 明确不做的 |
|---|---|---|
| 人人有期待 | 每人核心心愿优先，余量补「最好有」 | 不为了压价牺牲「必须要」 |
| 整单更划算 | 硬约束不动，逐人取最省搭法 + 试券 | 不堆配餐凑数 |
| 一起尝点新 | 心愿骨架 + 共享新品/限时项 | 预算不够就不加，不制造假差异 |

结果收敛时如实标注「与 X 策略收敛」并解释原因，**不为了形式制造无效差异**。

## D-07 分账口径（可复算）

归属项全额计入本人；共享项按人数均摊（分位差额从第一人起补足）；
优惠按占比分摊（最大余额法补平）。**不变量**：`Σ每人应付 == 官方核价实付`，前端底部实时校验。

## D-08 只读优先：不代下单、不领券

`create-order` / `auto-bind-coupons` / `mall-create-order` 一律不调用。
下单会真实扣款、不可撤回，与「先点好、再留念」的产品定位冲突；
闭环缺口用「只读关联真实订单」（`order-list` / `query-order`）补上。
**订单号只在本地，界面显示后 4 位，票根完全不出现。**

## D-09 失效与降级：不编造、不掩盖

- 网络失败：有历史快照 → `source=replay` + 原始 `dataTime` + 页面「离线回放·非实时」横幅；无快照 → `unavailable`。
- 失败结果只缓存 5 秒（`FAIL_TTL`），避免一次抖动被钉死几分钟。
- 核价失败时金额显示「未知」，方案不可选，**不用估算值冒充成交价**。
- 清理数据时如实回报 `removed / failed / remaining`，不谎称「已清干净」。

## D-10 票根只呈现最终确认方案的事实

字段全部来自 `party.confirmedPlan` 与用户主动填写的内容；默认隐藏订单号、门店详址、个人预算、
个人分摊、实际支付金额。状态只有「计划中 / 已完成」，`completed` 需用户主动确认。
裁剪（餐品/心愿条数）优先保信息密度，不减字号到不可读。

## D-11 金额一律以「分」为内部单位

官方菜单价是「元字符串」，核价返回「分」。适配层统一用 `Decimal + ROUND_HALF_UP` 转换，
规则层与预算校验复用同一函数——两套换算口径在 `1.005` 这类边界值上会差 1 分，属最难查的账目问题。

## D-12 P1：偏好复用只带心愿，不带价格

逐人授权（默认不勾选），只存昵称 + 三档心愿，**不存个人预算/订单/金额**。
「再聚」生成 draft（`plans=[]`、`dataTime=null`），菜单与核价强制重查——**旧价格绝不沿用**。
偏好组不足 3 人时补空位让用户填第 3 人，而不是抛「人数不合法」。

## D-13 取餐方式：只开到店自取 + 得来速

外送/团餐需要 `delivery-query-stores` 与不同 `orderType`，未验证，按「未验证不写入承诺」不开放。
界面只给用户这两个选项，不存在「点了报错」的死路。
